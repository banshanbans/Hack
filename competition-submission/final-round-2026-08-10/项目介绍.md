# 长者友好家（AnjuGuard）项目介绍

> **一句话介绍：** 对着父母家的真实空间拍一拍、问一问，AI 帮家庭发现画面中可见的跌倒、通行、支撑、照明与使用风险，标出具体位置，再由确定性规则生成可比较的 A/B/C 整改方案、参考预算和行动清单。

> **参赛方向：** 视觉搜索——视觉 + 语音，所见即所想。

## 0. 阅读说明：我们如何区分现状与规划

为避免把代码完成度、外部验收和未来设想混为一谈，本文使用三种状态：

| 状态 | 含义 |
|---|---|
| **已实现** | 仓库已有主路径代码和相应自动化验证 |
| **已实现，待外部验证** | 已有代码，但依赖功能开关、真实模型账号、真机或多设备验收 |
| **规划中** | 目标产品方案或理想 Agent Workflow，不作为当前能力宣传 |

当前最稳定的比赛主链路是照片评估。实时视觉语音、iPhone 深度定位等能力已有代码，但仍明确标注外部验证边界；整改后自动复查和抖音生态承接属于规划内容。

## 1. 我们解决的真实问题

父母年龄增长后，家中原本习以为常的环境可能逐渐变得不友好：松动地垫、洗浴区缺少支撑、夜间照明不足、门槛高差、通道杂物、常用物品摆放过高。成年子女通常知道“应该注意安全”，却很难回答三个更实际的问题：

1. **问题到底在哪里？**
2. **哪一项最值得先改？**
3. **不大装修的情况下，今天能做什么？**

专业适老化服务往往在家庭已经决定装修后才介入，普通家庭缺少一个低门槛的前置工具。长者友好家不是让 AI 泛泛地说“注意防滑”，而是把视觉证据、家人情况、规则判断和整改选择组织成一次可以马上开始的家庭行动。

### 一个真实、自然的触发场景

周末回家时，女儿发现父亲走路比以前慢，近半年还摔过一次。她站在卫生间门口，看到淋浴区、地垫和门槛，却不知道哪处真正值得担心，也无法用专业术语描述。

她打开长者友好家：

```text
选择父亲的行动能力与跌倒情况
  → 选择“卫生间”
  → 从门口拍一张全景，再补拍淋浴区和门槛
  → 系统检查照片是否清晰、是否拍到主要地面
  → AI 在原图上标出可见风险区域并解释原因
  → 她确认或否认风险，也可以修正位置
  → 比较“当天止险 / 推荐改造 / 专业改造”三档方案
  → 选择合适方案，生成参考预算和家庭整改清单
  → 分享给家人讨论，整改后重新拍摄复查（规划中）
```

这是家庭原本就会发生的“拍一下、看一下、问一下”，不是为了展示视觉模型而生造的场景。

## 2. 为什么必须用视觉 + 语音

### 视觉解决“说不清”

用户往往不知道“防滑系数”“通行净宽”“支撑点”等术语，但可以直接拍到门槛、地垫、浴室地面或床边通道。视觉输入能同时表达主体、位置、关系与环境状态，让风险说明落到具体证据区域。

### 语音解决“操作和追问成本”

用户一边举着手机，一边很难输入长文本。自然问题通常是：

- “这个地方有什么问题？”
- “这里能不能装扶手？”
- “我预算不多，先做哪一项？”
- “还需要补拍哪里？”

语音让用户不必先把画面翻译成文字，AI 再根据当前房间、画面和已有正式结果回答。实时相机中的建议只用于引导和待确认提示，不直接给最终等级、分数或价格；用户保存的代表画面仍需进入正式照片分析。

### 相比纯文字的明确增益

| 纯文字问答 | 长者友好家的多模态方式 |
|---|---|
| 用户必须准确描述陌生设施和相对位置 | 直接拍摄并在原图定位 |
| 容易得到泛化安全常识 | 回答绑定房间、证据区域和家人档案 |
| 难以判断用户漏拍了什么 | 独立输出覆盖度和补拍建议 |
| 建议与现场位置脱节 | 风险、方案和报告保留证据引用 |
| 举着手机时输入成本高 | 可通过语音快速追问和确认 |

**状态说明：** 照片主链路已实现；实时视觉语音顾问已实现代码但默认受功能开关控制，仍需真实供应商、Safari/Chrome、App 内 WKWebView、LiDAR/非 LiDAR 和弱网外部验证。

## 3. AI / Agent Workflow 如何自然发挥作用

长者友好家采用“模型理解、规则裁决、Agent 编排、前端确定性渲染”的分工，避免让一个大模型包办所有决策。

```text
需求理解
  → 视觉与场景理解
  → 候选风险发现
  → 证据区域定位
  → 跨图/跨帧风险归一化
  → Schema 与风险白名单校验
  → 确定性规则裁决
  → 安全参考分 + 独立覆盖度
  → A/B/C 方案与 PriceRule 预算
  → 报告生成
  → 满足判断
      ├─ 信息不足：只追问一个关键问题
      ├─ 覆盖不足：给一个具体补拍动作
      ├─ 需要决策：等待用户明确选择方案
      └─ 已满足：给出下一项可执行行动
```

### 各层责任

| 层级 | 责任 | 明确不做 |
|---|---|---|
| 视觉/语言模型 | 理解画面和用户问题；发现、定位、解释候选 | 不决定最终等级、分数或价格 |
| 确定性规则 | 校验风险代码和证据；决定等级、扣分、覆盖度、方案与价格 | 不猜测画面外事实 |
| Assessment Agent | 管理 Session、多房间状态、Skill 调用、超时、重试、反馈和满足判断 | 不绕过规则改变业务结论 |
| H5/iOS 前端 | 稳定渲染区域、结果、方案和报告；收集用户确认 | 不执行模型生成的 HTML/SVG/脚本 |

### 核心 Skills

- `MediaQualityCheckSkill`：判断照片能否支持分析，并给出补拍动作。
- `SceneUnderstandingSkill`：识别房间、设施、地面、通道和关系。
- `RiskDetectionSkill`：在风险白名单内发现候选。
- `RegionGroundingSkill`：返回 0–1 归一化 bbox/polygon。
- `RiskNormalizationSkill`：评分前合并同一物理风险的多视角证据。
- `CameraSuggestionSkill`：实时相机临时建议，不计分。
- `RecommendationSkill`：从规则允许的 A/B/C 方案中组织解释。
- `PriceExplanationSkill`：解释结构化 PriceRule，不改数字。
- `ReportSummarySkill`：把正式结果转成家庭可理解的行动摘要。
- `ReassessmentComparisonSkill`：比较整改前后证据，当前为规划能力。

完整理想化 Workflow 已封装为独立 Skill 包；当前可执行分支继续调用现有 v2 Assessment API，规划分支必须先做能力协商，不能假装已调用。

## 4. 用户最终获得什么

### 从“感觉不太安全”到“知道问题在哪里”

每个进入正式结果的风险必须具有可追溯证据。用户在原图上看到位置、原因和确认状态，而不是得到一段无法核对的泛化回答。

### 从“照片没拍全”到“知道还缺什么”

安全参考分和拍摄覆盖度完全分开。未拍到不等于安全，也不会直接扣安全分；覆盖不足时只显示“当前已检查区域安全参考分”，并提示缺失视角。

### 从“建议太空泛”到“三档可比较方案”

- **A：立即止险。** 低成本、通常当天可完成，但改善有限。
- **B：推荐改造。** 性价比优先，可以高亮但不自动选择。
- **C：专业改造。** 更长期、系统，可能需要施工或专业安装。

金额来自版本化价格规则，由代码合计并处理多个风险共用的整改动作。模型只能解释，不能修改数字或承诺确定报价。

### 从“一个人担心”到“家庭可以共同推进”

报告把风险证据、优先级、已选方案和参考预算放在同一清单中，便于子女、老人和其他家人讨论。未来复查能力将把“已整改”与“已验证解决”分开，形成真正的行动闭环。

## 5. 核心创新点

### 5.1 证据优先，而不是答案优先

正式风险必须关联 bbox、polygon、RoomPlan 对象/表面、快照、世界坐标或用户圈选之一。缺少证据的内容只能作为待确认提示。

### 5.2 模型理解，规则裁决

模型擅长理解复杂画面，规则擅长稳定、可解释、可复现的判断。相同输入和规则版本应得到相同评分与价格，不把安全结论交给一次不可复现的自然语言生成。

### 5.3 覆盖度与安全分解耦

这避免了“没拍到就当没问题”的常见误导，也避免为了提高分数而鼓励少拍照片。

### 5.4 连续看到不等于重复扣分

同一物理问题可能出现在多张照片或连续相机帧。系统保留多个证据视角，但评分前归一化为一个 canonical risk，只扣分一次。

### 5.5 H5 统一旅程，原生能力按需出现

iOS 以线上同源 H5 承担 P01—P09；原生只在单张拍照和实时空间扫描时出现。支持可靠深度时可在扫描期间显示临时世界锚点；无可靠深度时降级为二维证据，不制造虚假空间定位。

### 5.6 正式、临时和 Demo 从架构上隔离

实时建议不进入正式风险；正式 Provider 失败不回退 Demo；Mock 必须显式开启。用户能知道自己看到的是正式结果、待确认建议，还是演示素材。

- FastAPI/Uvicorn v2 Assessment API 与 SQLite 持久化。

- 确定性评分、独立覆盖度、用户反馈重算、预算分组去重和预计改善区间。
- H5 实时相机的质量/变化/单请求门控和不计分临时建议路径。
- iOS 持久化 WKWebView、Native Bridge、单张拍照、RoomPlan/ARKit 双模式扫描、代表帧上传和二维降级代码。
- Swift、Python/FastAPI、React/Vitest、产品文案和规则校验。

### 已实现代码，待外部验证或受功能开关控制

- 扫描页视觉语音 AI 适老顾问和实时视觉 Function Calling。
- 首页通用文字/纯音频 AI 适老顾问。
- H5/iOS RTC 席位、排队、租约、重连、打断和弱网降档。
- LiDAR 真机中的旋转图片、模型 bbox、深度图和世界锚点整体坐标一致性。
- Safari、Chrome、App 内 WKWebView 的相机/麦克风、弱网、VoiceOver 和 Dynamic Type 验收。
- 授权评测集上的真实召回、误报、定位和建议可用性结论。

### 规划中

- 整改前后自动对照，输出已解决、未解决、变化待确认和新候选。
- 分房型、风险、光照和设备的授权评测体系。
- 按城市、房屋条件和安装条件扩展 PriceRule。
- 家庭成员分工、备注和整改进度协作。
- 抖音内容/搜索触发与 H5 承接，以及匿名聚合洞察反哺内容。

### 明确不做

- 本地视频文件选择、自动关键帧截取、代表帧选择或视频帧正式识别。
- 医疗诊断、建筑验收、消防检查、无障碍认证或施工确定报价。
- 对未拍摄区域作安全推断。

## 7. 抖音生态如何放大：规划方案，不是当前上线能力

长者居家安全天然存在大量“看得见、说不清、想马上验证”的内容触发：卫生间防滑、夜间起身、门槛改造、扶手位置、轮椅通行、老房照明。抖音的短视频、搜索、达人内容和评论互动可以放大这些真实需求，但产品承接必须回到用户自己的家庭空间，而不是停留在观看知识。

### 规划闭环

```text
适老安全短视频 / 搜索词 / 达人案例
  → 内容卡片解释“什么场景值得拍一下”
  → 进入长者友好家 H5，选择房间并上传自家照片
  → 获得证据化风险与 A/B/C 行动清单
  → 分享给家人讨论，完成一项整改
  → 在用户授权前提下发起复查
  → 匿名聚合高频问题、补拍失败点和方案偏好
  → 反哺下一轮内容选题和拍摄指导
```

### 内容与产品的分工

- 内容负责触发认知：“这个常见布置可能值得检查”。
- 产品负责个体化验证：“在你父母家提供的画面中，证据在哪里”。
- 报告负责承接行动：“先改哪项、有哪些预算档位、如何和家人讨论”。
- 聚合数据只用于经过授权和匿名化的产品分析，不把真实家庭照片用于公开内容。

### 冷启动思路

1. 从卫生间、卧室夜间起身和玄关门槛三个高频场景开始，不一开始覆盖所有居住问题。
2. 与适老改造、养老照护、家居收纳和医生科普类创作者共创“拍摄检查清单”，但不让内容替代正式评估。
3. 在内容中使用一个明确动作：“回家从门口拍一张能看到主要地面的照片”。
4. 用 H5 完成低门槛承接，不要求先下载 App 或注册账号。
5. 以风险到行动转化和复查为长期价值，不以单纯曝光量作为成功标准。

本文不宣称已经接入抖音 API、完成站内发布或获得真实增长数据。

## 8. 增长与 ROI：先定义可验证漏斗，不虚构成绩

### 北极星方向

**帮助一个家庭完成并验证一项重要整改。**

短期用“有效检查完成”和“风险到行动转化”衡量产品是否真正解决问题，长期再观察复查和家庭协作。

### 指标体系

| 阶段 | 指标 | 计算方式 |
|---|---|---|
| 内容触发 | 入口点击率 | 进入检查入口人数 / 内容或搜索落地页曝光人数 |
| 拍摄表达 | 有效媒体率 | 至少一张照片通过质量检查的任务 / 开始上传的任务 |
| 价值到达 | 首次检查完成率 | 获得正式房间结果的任务 / 创建评估的任务 |
| 结果可信 | 风险确认率 | 用户确认成立的正式风险 / 展示的正式风险 |
| 行动选择 | 方案选择率 | 至少选择一项方案的报告 / 完成检查的报告 |
| 家庭协作 | 报告分享率 | 产生有效分享的报告 / 完成检查的报告 |
| 闭环价值 | 复查率 | 发起整改后复查的报告 / 有已选方案的报告 |
| 最终行动 | 风险到行动转化率 | 进入已处理或复查状态的风险 / 用户确认成立的风险 |
| 经营效率 | 单次有效检查成本 | 模型、媒体、计算与服务成本 / 完成的有效检查数 |

### 验证方法

- 冷启动阶段先建立基线，不预填未经实验的提升数字。
- 每轮只改变一个变量，例如内容入口、拍摄引导或结果表达。
- 同时观察完成率、误报反馈、退出率和单位成本，避免只提升点击却降低可信度。
- 模型优化需同时通过效果、延迟、成本和安全边界门禁。
- 抖音承接是否成立，以“进入后完成有效检查并采取行动”为准，而不是只看 PV。

### ROI 逻辑

投入主要来自模型调用、媒体处理、产品研发、真机验收、评测数据建设和内容合作；产出首先是更高的有效检查完成率、更低的无效调用、更高的方案选择与复查比例。未来商业化可以探索机构版评估、社区服务工具或合规的专业服务承接，但当前产品不以自动下单或施工佣金作为已实现能力。

## 9. 技术架构

| 层 | 技术与责任 |
|---|---|
| H5 | React 19 + TypeScript + Vite；承担照片、实时相机和 P01—P09 用户旅程 |
| iOS | UIKit + WKWebView + RoomPlan + ARKit + RealityKit；承担原生采集、深度定位和扫描期提示 |
| 服务端 | FastAPI + Uvicorn + SQLite；承担 Session、媒体、任务、Provider、规则、报告与分享 |
| 领域层 | Swift Package `AnjuCore`；承担风险模型、证据、状态、规则与坐标解析 |
| AI Provider | 火山方舟 / OpenAI Responses；仅服务端持有密钥，输出必须通过 Schema 和白名单 |
| 规则数据 | 版本化 JSON；风险、评分、覆盖度、A/B/C 和价格数字不写进 Prompt |

## 10. 后续路线

1. 完成 Safari、Chrome、WKWebView、LiDAR/非 LiDAR 和弱网外部验证。
2. 建立获授权的照片与实时相机评测集，公开可复现的分层指标。
3. 上线整改前后复查，使“完成整改”与“验证解决”真正分开。
4. 在规则框架内扩展城市和安装条件价格，不让模型自由报价。
5. 小范围验证抖音内容到 H5 有效检查的承接漏斗，再决定规模化投入。

## 11. 负责任声明

长者友好家是基于用户所提供画面的环境安全辅助筛查工具，不是医疗诊断、建筑验收、无障碍认证、消防检查或施工报价工具。它只能分析画面中可见内容，不会将未拍摄区域视为安全，也不对墙体、承重、防水、暗管和施工条件作照片外判断。
